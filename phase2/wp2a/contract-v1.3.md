## 0. Why v1.2 was rejected

No Step-2 extraction, fixture evaluation or mutation run occurred under v1.2. Review found that
its scientific registration still could not determine its own result without later choices:

1. the ROCIT member was called `opaque` merely because WP2A had not re-inspected it, although its
   resolvable container and authenticated member selector make the member retrievable;
2. `known_from` was set to retrieval time, including a cross-origin equality asserted before the
   second occurrence existed;
3. Q7 omitted the informative `valid_from.not_later_than` bound;
4. most expected answers had no explicit evidence and interpretation pointers;
5. Q3 was cardinalized per output although Family A contains two transformations per output, and
   its transformation record was incomplete;
6. M2 was said to have “no output entity” while Q9 required an RDF identifier denoting that output,
   leaving the distinction semantically impossible or syntactically gameable;
7. the cross-family decision rows overlapped; and
8. the execution order never froze the evaluator before the evaluator could inspect fixtures.

v1.3 corrects those scientific-registration defects. The companion Step-2 and mutation artifacts
correct the execution-registration defects separately.

## 3. The two models

Both models must supply an addressable identifier for every transformation output. The distinction
is whether that identifier receives a separately described and typed output node.

**M1 — explicit output node.** The graph contains a node whose `@id` is the output identifier,
whose `@type` includes `ftro:TransformationOutput`, and whose digest and size describe that byte
state. Transformation assertions refer to that node.

**M2 — assertion-carried output identity.** A named transformation-assertion node carries the
source occurrence, procedure, output identifier, digest and size. The output identifier may occupy
an RDF subject or object position, but the graph contains **no separate node description and no
`rdf:type ftro:TransformationOutput` statement for it**. An RDF resource reference is not denied;
only the separately described/typed output record is absent.

This wording replaces v1.2's impossible shorthand “no output entity”. A dangling identifier, a
literal digest, the assertion's own identifier reused as the output identifier, and an untyped
self-loop do not satisfy either model's output-identity requirement.

M1 is a strict representational extension of M2 for this trial: the corresponding M1 fixture is the
M2 graph plus a separately described and typed `ftro:TransformationOutput` node for each distinct
output. It removes or changes no M2 statement and changes no normalized Q1–Q8 fact. Consequently,
an M2 family pass implies an M1 pass for that family. Observing M2 pass while M1 fails is an
evaluator, fixture-construction or registered-relation assurance failure—not evidence that M2 is
more expressive.

## 4. Three independent state axes

The axes answer different questions and MUST NOT be inferred from one another.

| Axis | Question |
| --- | --- |
| `evidence_state` | Can the identified evidence artifact be retrieved and inspected under the recorded access conditions? |
| `verification_result` | What does that evidence support about this assertion? |
| `execution_status` | Was the named verification procedure executed in the run or historical carrier cited by this assertion? |

The ROCIT container **and selected member are `resolvable` before Step 2**: the immutable container
route is recorded and the member selector is authenticated. The selected member's byte identity is
nevertheless `verification_result: indeterminate`, and the independent WP2A Step-2 procedure is
`not_attempted`. A successful Step 2 changes those latter facts; it does not manufacture
resolvability.

SIO containers are `resolvable`. BKG containers are `opaque` from the recorded environment because
they are identified exactly but the route was unreachable. The historical report about the BKG
retrieval is a different artifact and is `resolvable`.

## 5. Bitemporal rule

`valid_from` concerns the represented relation. It is unknown and carries an upper bound:

- for a one-occurrence transformation, `not_later_than` is that occurrence's `retrieved_utc`;
- for a cross-origin equality, `not_later_than` is the later of the two occurrences' retrieval
  times, so the relation is never bounded by only one object.

`known_from` concerns FTRO's evidence-backed knowledge. Retrieval time alone is not an exact
knowledge time. It is an interval:

- `not_earlier_than` is the latest prerequisite-evidence time;
- `not_later_than` is the timestamp of the first cited durable carrier that contains the evidence
  needed for the registered assertion; and
- for a cross-origin assertion, prerequisites include **both** objects.

`valid_to` and `known_to` are open. Every bound records the exact source pointers and the operation
(`identity` or `max`) by which it was obtained. No `known_from` bound may predate any evidence it
requires.

## 7. Query and model-pass rule

`queries-v1.3.json` is normative. Q3 returns one complete record per transformation, not one per
distinct output. Its record includes the assertion identifier, source occurrence, procedure
identity and implementation, output identifier, digest, size and member selector when applicable.

Q7 returns the predicate, subject, object, evidence artifacts, all three state axes and all temporal
values and bounds per assertion. Q9 reports both output addressability and whether a separately
described/typed output node exists; it does not require M2 to pretend an RDF resource is not a
resource.

A model passes a family only when every applicable query returns exactly the expected records and
fields at the declared cardinality, with no missing or extra answer. Applicability, expected-answer
pointers and cardinalities are machine-readable in `queries-v1.3.json`; every pointer terminates at
one exact array in `expected-answers-v1.3.json`. Fixtures contain raw graph statements, never copies
of those normalized arrays, and the evaluator must derive each answer from the graph.

## 8. Total, mutually exclusive decision function

First apply these run-level gates in order. The first matching gate is final:

1. an undetected registered fault, or a detected registered presentation-only mutation →
   `mutation_assurance_failed`;
2. a mutation, reset, evaluator or required query did not execute → `not_executed`;
3. required evidence is insufficient after Step 2 → `indeterminate_evidence`;
4. M2 passes a family that M1 fails → `model_relation_assurance_failed`;
5. otherwise apply the complete relation-consistent Boolean table below.

`1` means that model passes that family. `0` means it executes and fails that family.

| M1-A | M1-B | M2-A | M2-B | Outcome |
| ---: | ---: | ---: | ---: | --- |
| 0 | 0 | 0 | 0 | `neither_supported` |
| 0 | 1 | 0 | 0 | `split_by_family` |
| 0 | 1 | 0 | 1 | `split_by_family` |
| 1 | 0 | 0 | 0 | `split_by_family` |
| 1 | 0 | 1 | 0 | `split_by_family` |
| 1 | 1 | 0 | 0 | `encoded_decoded_supported` |
| 1 | 1 | 0 | 1 | `split_by_family` |
| 1 | 1 | 1 | 0 | `split_by_family` |
| 1 | 1 | 1 | 1 | `equivalent_for_registered_queries` |

These nine rows are disjoint and exhaustive after gate 4; that gate catches the other seven Boolean
tuples. Any within-model family split therefore has exactly one outcome and never closes
`FTRO-P1-DEF-010`. `equivalent_for_registered_queries` is a legitimate bounded result: it says the
registered questions do not discriminate between the two representations, not that one fixture
won a competition whose expected answers were written differently for it.

## 9. Evaluator freeze and execution order

1. Freeze the complete v1.3 registration set listed in §1. **No execution.**
2. Add, test and bind `run_step2_v1_3.py`; until the manifest reports the exact runner as `ready`,
   stop. This step changes no evidence state and reads no provider payload.
3. From a clean published commit, execute Step 2 once. Any outcome other than `step2_supports`
   halts this candidate.

The Step-2 instrument executes the registered JSON-Schema vocabulary as well as its cross-field
checker, resolves both from the report's subject commit, and accepts only a subject contained in a
remote-tracking ref. Each input path is read once; its digest and size authenticate that captured
byte string. Both extraction routes consume anonymous seekable file descriptors populated only
from the capture and never reopen the provider pathname. After all methods, the current pathname
is rehashed solely as mutation evidence; a match or mismatch cannot validate, replace or alter the
bytes consumed, and drift is `step2_evidence_assurance_failed`. Every malformed or non-supporting
candidate is preserved by create-without-overwrite at a run-specific rejected path.

Every report also carries the exact registered `outcome_interpretation_bound`. A
`step2_supports` outcome establishes byte-for-byte agreement between the two registered extractors
and reproduction of the committed optical expectation. It does not establish that the expected
member digest and size were derived independently of the pre-existing ignored extracted copy, nor
does it prove the prior claim's external timestamp or make the value provider-attested.

Before any provider pathname opens, the runner must reproduce an FTRO-synthetic sentinel through
the same POSIX `/dev/fd` plus inherited-descriptor transport. If that capability probe fails, Step 2
has not started. Once input capture succeeds, snapshot allocation or method-start failure is a typed
non-execution row, so the complete candidate is preserved rather than lost as a traceback.

4. Before any fixture bytes exist, write and freeze `evaluate_v1_3.py` and
   `evaluator-binding-v1.3.json`. The binding records evaluator digest, query digest, the exact
   `expected-answers-v1.3.json` digest and inputs, decision-table digest and the four expected fixture identifiers. The evaluator is run
   against synthetic self-tests only; it does not inspect a trial fixture at this stage.
5. Hand-author the four fixtures satisfying the frozen fixture requirements.
6. Freeze executable mutation recipes, including exact R11 target-set equality against the actual
   distinct entity identifiers; run one explicitly non-qualifying calibration.
7. A repair to the evaluator after any fixture exists creates a new contract version and new
   fixture identifiers. Prior fixtures remain visible but non-qualifying.
8. Run one qualifying comparison from a clean checkout, publish per-query and per-family results,
   apply §8 once, and stop.

No evaluator, query, expected-answer binding, fixture or mutation recipe may change after a
qualifying result is observed.

## 10. Stopping and scope

The trial stops after the registered target population is exhausted and one §8 outcome is emitted.
`FTRO-P1-DEF-010` closes for `encoded_decoded_supported` or
`equivalent_for_registered_queries`. Equivalence is a result, not permission to choose
aesthetically; it leaves any later representation choice to a separately registered criterion.

Out of scope: profile amendment, Gate-1 rerun, full ancestry graph, BKG re-retrieval, resolver,
browser, third family and general RO-Crate conformance. Any change to this scope after execution
begins creates a new contract version and restarts the trial.
